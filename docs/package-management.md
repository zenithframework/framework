# Zenith Framework — Package and Composer Specification

**Status:** Proposed baseline

## 1. Purpose

Zenith uses Composer as its package manager and autoloader. The repository may be a monorepo for first-party package development, while each independently distributable subsystem remains an actual Composer package.

## 2. The four concepts

| Location/concept | Meaning |
|---|---|
| `packages/` | First-party source workspace in this repository |
| `vendor/` | Composer's installed dependency directory |
| Packagist/private Composer repository | Distribution/catalog source for released packages |
| Root `composer.json` | Project dependency graph, scripts, repositories and autoload configuration |

A directory under `packages/` is not independently installable until it has a valid package manifest and a resolvable dependency graph.

## 3. Package requirements

Each independent package MUST include:
- unique Composer package name (e.g. `zenith/orm`);
- `type: library` unless a different type is justified;
- supported PHP constraint;
- PSR-4 autoload mapping;
- explicit runtime dependencies;
- development dependencies and test commands;
- a README with installation and public API usage;
- license and changelog/release notes;
- semantic versioning policy;
- no dependency on the root application project.

Package APIs SHOULD depend on contracts instead of concrete sibling internals. Avoid circular dependencies and hidden reliance on root-level autoload aliases.

## 4. Local development with path repositories

Example root `composer.json` excerpt:

```json
{
  "repositories": [
    {
      "type": "path",
      "url": "packages/*",
      "options": { "symlink": true }
    }
  ],
  "require": {
    "zenith/contracts": "@dev",
    "zenith/container": "@dev",
    "zenith/database": "@dev",
    "zenith/orm": "@dev"
  },
  "minimum-stability": "dev",
  "prefer-stable": true
}
```

Use development constraints only for a development branch/workspace. Released applications SHOULD consume tagged stable versions and commit their lock file.

Example `packages/orm/composer.json`:

```json
{
  "name": "zenith/orm",
  "type": "library",
  "require": {
    "php": "^8.5",
    "zenith/contracts": "^1.0",
    "zenith/database": "^1.0"
  },
  "autoload": {
    "psr-4": {
      "Zenith\\ORM\\": "src/"
    }
  }
}
```

The example assumes those package names and release constraints have been established. Align constraints with actual tagged versions; do not copy placeholders into a release manifest.

## 5. Install and development commands

- `composer install` installs the lock-file graph.
- `composer update` intentionally resolves a new dependency graph; do not use casually in CI or production deployment.
- `composer dump-autoload` regenerates autoload metadata.
- `composer validate` validates manifests.
- CI MUST install from a clean checkout and verify local path package resolution.
- Release CI MUST test each package from an archive/tag or isolated consumer project, not only from the monorepo autoloader.

## 6. Vendor rules

- `vendor/` is generated by Composer and MUST be ignored by Git in normal application/repository workflows.
- Never edit files under `vendor/`.
- Never put first-party source in `vendor/` manually.
- A production deployment runs Composer install from a trusted lock file.
- Autoload files MUST be generated from package metadata; avoid duplicate hand-maintained class maps.

## 7. Versioning and compatibility

Use SemVer for released public packages:
- patch: backward-compatible fixes;
- minor: backward-compatible features;
- major: incompatible public API changes.

Document PHP-version support, extensions, database driver versions and peer dependencies. Deprecate before removal when feasible. Cross-package release compatibility MUST be tested as a supported version matrix.

## 8. Package discovery and providers

Package discovery MUST be deterministic. A package may declare provider metadata only through a documented manifest convention. Discovery MUST NOT execute arbitrary package code merely to inspect metadata. Applications must be able to disable optional providers and understand which package registered a service.

## 9. Extraction policy

Start with a cohesive source boundary. Extract a subsystem only when it has a stable API, clear dependency direction, independent tests and a real reuse/release need. Move source atomically and update namespaces, tests, docs and autoloading. Do not retain duplicate implementations in `core/` and `packages/`.
